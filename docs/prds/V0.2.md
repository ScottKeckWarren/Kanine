# Kanine V0.2 — Product Requirements Document

> Closes the loop: pups receive a label-driven prompt, report live status, and signal
> completion so the supervisor knows when to assign the next task.

- **Version:** 0.2.0
- **Status:** Draft
- **Builds on:** V0.1 (supervisor + pup dispatch loop, `POST /pups/register`, `POST /pups/{id}/poll`)
- **No TUI in this release** — all output logged to screen and file via Monolog.
- **No git worktrees in this release** — pups still work in their current directory.

---

## 1. Summary

V0.1 proved the end-to-end dispatch loop: supervisor queues GitHub Issues, pup polls,
pup runs `claude --headless`. Three gaps remain:

1. **No custom prompt.** Claude receives a hardcoded `"Working on: {title}\n\n{body}"`.
   There is no way to give Claude project-specific context or instructions.
2. **No live status.** Once a pup starts Claude, the supervisor is blind — it cannot
   show what Claude is currently doing.
3. **No completion signal.** Supervisor never learns the task is done, so the pup is
   stuck in `Working` forever and cannot be assigned the next task without a restart.

V0.2 closes all three gaps with minimal scope:

- Each GitHub label can have a dedicated prompt file at `.kanine/labels/{label}/prompt.md`.
  When an issue is queued, `IssueLoader` walks the issue's labels, loads the first matching
  prompt file, and stores it in `Task.prompt`. Falls back to a built-in default if no file
  is found. No config keys required — the prompt lives with the repo.
- Pups call `POST /tasks/{id}/status` periodically to report the current line of
  Claude output, surfaced in supervisor logs.
- Pups call `POST /tasks/{id}/complete` when Claude exits, returning the outcome.
  Supervisor marks the pup idle and optionally writes a GitHub label.

## 2. What Ships in V0.2

### Included

- Label-based prompt files: `.kanine/labels/{label}/prompt.md` resolved per issue at queue time into `Task.prompt`.
- `ClaudeRunner` updated to build: `{prompt}\n\n## Issue #{number}: {title}\n\n{body}`.
- `POST /tasks/{id}/status` endpoint — pup posts the latest Claude output line; supervisor logs it.
- `POST /tasks/{id}/complete` endpoint — pup posts outcome (`success` | `failure`) + summary; supervisor marks pup `Idle`.
- GitHub label write-back on completion: supervisor instructs pup which labels to add/remove; pup applies them.
- PHPUnit tests for all new logic.

### Explicitly Out of Scope

- Per-dispatch prompt input (TUI input widget — future release).
- Question/answer flow (`POST /tasks/{id}/questions`) — deferred; in protocol doc but not implemented.
- Git worktrees — still future.
- Task queue persistence (in-memory only; lost on supervisor restart).
- TUI rendering — still logging-only.
- Concurrent tasks per pup (blocked-task second-assignment flow).
- TLS / remote pups.

## 3. Domain Model Changes

### 3.1 `Task` gains `labels`; `Prompt` is a pup-side value object

Prompts are resolved by pups from their own working directory, not by the supervisor.
The supervisor cannot know which project a pup is running in — it may be serving
multiple repos simultaneously. Instead, `Task` carries the issue's raw labels so each
pup can resolve the correct prompt locally.

```php
// src/Domain/Task.php
final readonly class Task
{
    public function __construct(
        public string    $id,
        public int       $issueNumber,
        public string    $repo,
        public string    $title,
        public string    $body,
        public array     $labels,      // NEW: string[], raw GitHub label names
        public TaskState $state,
    ) {}
}
```

`Prompt` is a value object used **on the pup side only** (`ValueObject\String\Prompt`).
It wraps a non-empty string and throws on construction if the value is blank.

```php
// src/ValueObject/String/Prompt.php
final readonly class Prompt
{
    public function __construct(public readonly string $value)
    {
        if (trim($value) === '') {
            throw new \InvalidArgumentException('Prompt cannot be empty.');
        }
    }

    public function __toString(): string
    {
        return $this->value;
    }
}
```

`PromptResolver` also lives on the pup side. It walks the task's labels in order,
looks for `.kanine/labels/{label}/prompt.md` in the pup's cwd, and returns a `Prompt`
instance — falling back to the built-in default if no file matches.

### 3.2 New: `UsageTracker`

Supervisor tracks the reported Claude session usage percentage across all active pups.
Pups report current usage on every poll and on task completion. Supervisor stores the
highest value seen. When usage reaches the configured threshold (default 90 %), no new
tasks are assigned until a pup reports a lower value (session reset).

```php
// src/Supervisor/UsageTracker.php
final class UsageTracker
{
    private float $usagePct = 0.0;

    public function __construct(private readonly float $throttleThreshold = 90.0) {}

    public function record(float $pct): void
    {
        $this->usagePct = max(0.0, min(100.0, $pct));
    }

    public function isThrottled(): bool
    {
        return $this->usagePct >= $this->throttleThreshold;
    }

    public function usagePct(): float
    {
        return $this->usagePct;
    }
}
```

The threshold is configurable via `agent.usage_throttle_pct` (default `90.0`).

### 3.3 `PupStatus` gains `Completed` and `Failed`

```php
enum PupStatus: string
{
    case Idle      = 'idle';
    case Working   = 'working';
    case Completed = 'completed';   // NEW
    case Failed    = 'failed';      // NEW

```

Supervisor resets pup to `Idle` after processing a completion.

### 3.3 `TaskState` gains `Complete` and `Failed`

```php
enum TaskState: string
{
    case Queued   = 'queued';
    case Assigned = 'assigned';
```

## 4. Functional Requirements

### 4.1 Label-based prompt resolution (pup-side)

- **FR-1** `IssueLoader` stores all raw GitHub label names on `Task.labels` (string
  array, order preserved from GitHub API response).
- **FR-2** The poll response includes `labels` in `new_task` and does **not** include
  a `prompt` field — prompt resolution is the pup's responsibility:
  ```json
  {
    "new_task": {
      "id": "...",
      "issue_number": 42,
      "repo": "owner/repo",
      "title": "...",
      "body": "...",
      "labels": ["kanine: ready", "bug"]
    }
  }
  ```
- **FR-3** On task receipt, pup runs `PromptResolver` against its own cwd. For each
  label in order, it checks for `.kanine/labels/{label}/prompt.md`. First match wins.
- **FR-4** Label names are used as directory names verbatim. Any label whose name
  contains `/` or a null byte is skipped with a warning log; resolution continues to
  the next label.
- **FR-5** If no label has a matching file, pup uses the built-in default:
  `"You are a software developer. Work the following GitHub issue to completion."`.
  Pup logs which prompt was resolved (file path or default).
- **FR-6** `PromptResolver` returns a `Prompt` value object (never null). The resolved
  value is passed to `ClaudeRunner`.
- **FR-7** `ClaudeRunner` builds the final Claude input as:
  ```
  {prompt}

  ## Issue #{issue_number}: {title}

  {body}
  ```

### 4.2 Task status endpoint

- **FR-7** Supervisor exposes `POST /tasks/{task_id}/status`.
- **FR-8** Request body:
  ```json
  {
    "pup_id": "uuid",
    "message": "string"
  }
  ```
  `message` is a short string (the latest meaningful line from Claude's output).
- **FR-9** Supervisor validates that `task_id` exists and `pup_id` is assigned to it.
  Returns `404` if task is not found; `403` if pup is not the assigned pup.
- **FR-10** Supervisor logs the status message with pup ID and task ID via Monolog.
- **FR-11** Response `204` — no body.
- **FR-12** Pup calls this endpoint every `status_interval_ms` (configurable, default 10 000) while Claude is running, forwarding the latest output line captured from the subprocess stdout.

### 4.3 Task completion endpoint

- **FR-13** Supervisor exposes `POST /tasks/{task_id}/complete`.
- **FR-14** Request body:
  ```json
  {
    "pup_id": "uuid",
    "outcome": "success | failure",
    "summary": "string"
  }
  ```
- **FR-15** Supervisor validates pup is assigned to the task. Returns `404` / `403` on mismatch.
- **FR-16** On valid completion:
  1. Updates `Task.state` → `Complete` or `Failed`.
  2. Unassigns task from pup.
  3. Resets pup status → `Idle`.
  4. Logs outcome and summary via Monolog.
- **FR-17** Response `200`:
  ```json
  {
    "label_actions": [
      { "remove": "kanine: ready" },
      { "add": "kanine: done" }
    ]
  }
  ```
  On `success`: remove `kanine: ready`, add `kanine: done`.
  On `failure`: remove `kanine: ready`, add `kanine: failed`.
  Label names are configurable via `github.labels` (see §5).
- **FR-18** Pup receives `label_actions`, applies each via the GitHub API, and logs the result.
- **FR-19** After calling `POST /tasks/{id}/complete`, pup resumes polling with `status: idle`.

### 4.4 Usage throttling

Claude Code sessions have a finite token budget per billing period. When that budget is
nearly exhausted, dispatching new work is wasteful — tasks would fail mid-execution.
`UsageTracker` lets the supervisor pause new assignments near the limit without stopping
in-flight work.

- **FR-23** Pups include a `usage_pct` float (0–100) in every poll request body and in
  every `POST /tasks/{id}/complete` request body, representing the current Claude
  session usage percentage as reported by the Claude Code process.
- **FR-24** `ClaudeRunner` captures usage from Claude's output. Claude Code headless
  mode writes a JSON summary line to stdout on exit; `ClaudeRunner` parses it and
  exposes `getUsagePct(): ?float`. If no usage data is available, pup sends `null` for
  `usage_pct` and supervisor ignores the field.
- **FR-25** Supervisor passes each non-null `usage_pct` value to `UsageTracker::record()`
  on every poll and completion.
- **FR-26** When `UsageTracker::isThrottled()` returns `true` (usage ≥ threshold),
  `HttpServer::handlePoll` returns `new_task: null` for all idle pups, regardless of
  queue depth, and includes `"throttled": true` in the poll response.
- **FR-27** When throttled, supervisor logs a warning once per throttle event (not on
  every poll) including the current `usage_pct`.
- **FR-28** When a subsequent poll or completion reports `usage_pct` below the threshold
  (session reset detected), `UsageTracker` records the new value, `isThrottled()`
  returns `false`, and normal assignment resumes. Supervisor logs the reset.
- **FR-29** Pup checks `throttled` in the poll response. If `true`, pup doubles its
  next poll delay (up to a configurable `max_throttle_poll_ms`, default 60 000) and
  logs "throttled — waiting for session reset". When `throttled` is absent or `false`,
  pup returns to the normal `poll_interval_ms`.
- **FR-30** The throttle threshold is configurable: `agent.usage_throttle_pct` (float,
  default `90.0`). Must be in range 50–99; supervisor logs an error and uses the
  default if outside range.

### 4.5 Pup changes

- **FR-31** On task receipt, pup reads `new_task.prompt` (deserializes to `Prompt` value
  object); passes it to `ClaudeRunner` alongside `title` and `body`.
- **FR-32** Pup captures Claude subprocess stdout incrementally (via `symfony/process`
  output callback). Every `status_interval_ms`, pup extracts the latest non-empty line
  and posts it to `POST /tasks/{id}/status`.
- **FR-33** When `ClaudeRunner` exits (exit code 0 = success, non-zero = failure), pup
  posts to `POST /tasks/{id}/complete` with the appropriate `outcome`, a trimmed
  last-N-lines summary, and the `usage_pct` parsed from Claude's exit output.

## 5. Config Schema (V0.2 additions)

```yaml
agent:
  status_interval_ms: 10000      # how often pup posts a status update while claude runs
  usage_throttle_pct: 90.0       # pause new assignments at this session usage %
  max_throttle_poll_ms: 60000    # max pup poll interval when throttled

github:
  labels:
    ready: "kanine: ready"    # label that marks an issue as queued
    done:  "kanine: done"     # label applied on successful completion
    failed: "kanine: failed"  # label applied on failure
```

`github.labels` values default to `kanine: ready`, `kanine: done`, and `kanine: failed`
if not provided. No prompt config — prompts live in `.kanine/labels/` files.

### Label prompt directory layout

```
.kanine/
└── labels/
    ├── kanine: ready/
    │   └── prompt.md          # prompt used when an issue has this label
    ├── bug/
    │   └── prompt.md
    └── feature/
        └── prompt.md
```

`prompt.md` is plain markdown. The entire file contents become the `Prompt` value passed
to `ClaudeRunner`. No template interpolation — the issue title and body are appended by
`ClaudeRunner`, not embedded in the prompt file.

This directory lives in the **pup's working directory**, not the supervisor's. Each
project a pup is checked out in can have its own `.kanine/labels/` tree with
project-specific prompts. The supervisor never reads these files.

## 7. Technical Notes

### 7.1 `PromptResolver` and path safety

`PromptResolver` runs on the pup. It constructs the candidate path as:

```php
$path = $basePath . '/.kanine/labels/' . $label . '/prompt.md';
```

`$basePath` is the pup's cwd at startup (`getcwd()`). Before reading, it must verify
`realpath($path)` starts with `realpath($basePath)` to guard against labels containing
`..` sequences. Any label that fails this check is skipped with a warning log — the
resolver moves on to the next label.

### 7.2 Incremental stdout capture

`ClaudeRunner` needs to capture stdout without buffering the whole output.
`symfony/process` supports an output callback:

```php
$this->process->start(function (string $type, string $buffer): void {
    foreach (explode("\n", $buffer) as $line) {
        $line = trim($line);
        if ($line !== '') {
            $this->latestLine = $line;
        }
    }
});
```

Pup reads `$claudeRunner->getLatestLine()` every `status_interval_ms` for the status post.

### 7.3 Summary on completion

When Claude exits, pup trims the last 10 lines of accumulated output and sends them
as `summary`. `ClaudeRunner` accumulates lines in a ring buffer (max 10) so no large
string is held in memory.

### 7.4 Label write-back

Pup applies label actions using the GitHub API via `knplabs/github-api` (already a
dependency). Labels are applied after `POST /tasks/{id}/complete` returns `200` with
`label_actions`. If GitHub API call fails, pup logs the error and continues — label
failure must not block the pup from accepting the next task.

## 8. Phases

### Phase 1 — Label-based prompt resolution

**Goal:** `Task.prompt` (as `Prompt` value object) resolved from `.kanine/labels/` files; `ClaudeRunner` uses it.

Tasks:
- Implement `Prompt` value object at `src/ValueObject/String/Prompt.php`; enforce non-empty on construction.
- Implement `Prompt` value object at `src/ValueObject/String/Prompt.php`.
- Add `string[] $labels` field to `Task`; remove any `prompt` field from `Task`.
- Update `IssueLoader` to populate `Task.labels` from GitHub API response.
- Update `HttpServer::handlePoll` to include `labels` array in `new_task` payload.
- Implement `PromptResolver` on the pup side: given a list of label names and a base
  path (pup cwd), walks labels in order, returns first `prompt.md` contents wrapped in
  `new Prompt(...)`, or `new Prompt(DEFAULT_PROMPT)` if no file found.
- Update pup to read `labels` from poll response, run `PromptResolver` locally, pass
  resulting `Prompt` to `ClaudeRunner`.
- Update `ClaudeRunner` to accept `Prompt` and build full input string.
- Unit tests: `Prompt` construction (valid, empty throws), `PromptResolver` (label match,
  no match → default, path traversal guard), `ClaudeRunner` command construction.

**Done when:** Pup runs Claude with `{file_prompt}\n\n## Issue #N: {title}\n\n{body}`.

### Phase 2 — Status reporting

**Goal:** Supervisor logs live Claude output from pups.

Tasks:
- Implement `POST /tasks/{id}/status` in `HttpServer`.
- Add `TaskRegistry` (or extend `TaskQueue`) to look up tasks by ID for validation.
- Update `ClaudeRunner` to capture stdout incrementally; expose `getLatestLine()`.
- Update pup loop to post status every `status_interval_ms` while Claude is running.
- Unit tests: `HttpServer` status endpoint (valid, task not found, wrong pup).

**Done when:** Supervisor log shows a live status line from each pup every 10 s while Claude works.

---

### Phase 3 — Completion reporting and label write-back

**Goal:** Pup signals done; supervisor marks pup idle; GitHub labels updated.

Tasks:
- Implement `POST /tasks/{id}/complete` in `HttpServer`; accept `usage_pct` in request body.
- Supervisor state transitions: `Task` → `Complete`/`Failed`, pup → `Idle`.
- Pass `usage_pct` from completion body to `UsageTracker::record()`.
- Build `label_actions` response from `github.labels` config.
- Update pup to call complete endpoint after Claude exits (with parsed `usage_pct`); apply label actions via GitHub API.
- Unit tests: completion endpoint (success, failure, wrong pup), label action construction.

**Done when:** After Claude exits, pup posts complete, supervisor log shows "pup X idle", GitHub issue has `kanine: done` (or `kanine: failed`) label applied.

---

### Phase 4 — Usage throttling

**Goal:** Supervisor pauses new assignments when Claude session usage ≥ threshold.

Tasks:
- Implement `UsageTracker` with `record()`, `isThrottled()`, `usagePct()`.
- Wire `UsageTracker` into `Supervisor`; pass threshold from config.
- Update `HttpServer::handlePoll` to call `UsageTracker::record(usage_pct)` from poll
  request; return `throttled: true` and skip task assignment when `isThrottled()`.
- Update `ClaudeRunner` to parse Claude's exit JSON for usage percentage; expose
  `getUsagePct(): ?float`.
- Update pup poll loop to include `usage_pct` in request; respect `throttled: true` by
  backing off to `max_throttle_poll_ms`.
- Unit tests: `UsageTracker` (below threshold, at threshold, above threshold, reset
  detected), `HttpServer` poll throttle branch (throttled returns no task + flag),
  pup backoff logic.

**Done when:** With a mocked `UsageTracker` returning `isThrottled() = true`, poll
response contains `throttled: true`, no task is assigned, and pup logs throttle warning
and backs off poll interval.

---

### Phase 5 — Integration and polish

**Goal:** V0.2 acceptance criteria all pass.

Tasks:
- End-to-end test: supervisor + one pup, real GitHub issue, real `claude --headless`. Verify prompt is received, status lines appear in log, completion fires, labels updated, usage throttle engages when mocked above threshold.
- Error paths: GitHub label API failure (log + continue), status post with unknown task ID, complete post with wrong pup, `Prompt` constructed with empty string.
- Config validation: clear error if `usage_throttle_pct` outside 50–99.
- Review log output for readability; ensure status lines are concise.
- Tag `v0.2.0` release.

## 10. Open Questions (pre-V0.3)

- **Git worktrees.** Still deferred. Decide clone strategy (supervisor pre-clones vs. pup clones on task receipt) before V0.3.
- **Task queue persistence.** In-memory queue lost on restart. SQLite sidecar or flat JSON sidecar candidates for V0.3.
- **Question/answer flow.** Protocol is defined (`POST /tasks/{id}/questions`) but not implemented. V0.3 candidate once completion loop is stable.
- **Per-dispatch prompt override.** User types a custom prompt when dispatching a card from the board (TUI input widget). Deferred until TUI navigation exists.
- **Pup deregistration.** `DELETE /pups/{id}` (protocol §4.6) not implemented. Stale pup detection (missed polls) is still future.
- **Concurrent tasks per pup.** One task per pup. Blocked-task second-assignment deferred until question flow is in place.
