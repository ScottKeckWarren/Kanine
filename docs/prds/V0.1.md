# Kanine V0.1 — Product Requirements Document

> First working release: a supervisor that queues GitHub Issues and dispatches them to
> pups running Claude Code headlessly in their current directory.

- **Version:** 0.1.0
- **Status:** Draft
- **No TUI in this release** — all output logged to screen and file via Monolog.
- **No git worktrees in this release** — each pup works in whatever directory it was started in.

---

## 1. Summary

V0.1 makes Kanine functional end-to-end at the smallest possible scope:

1. A **supervisor** process reads GitHub Issues tagged `kanine: ready`, builds a task queue, and serves a minimal HTTP API.
2. One or more **pups** register with the supervisor, poll for task assignments, and run `claude --headless` in their current working directory to work each assigned issue.
3. Everything is logged to screen and file via Monolog. No TUI, no git worktrees, no question/answer flow.

The goal is a working pipeline that proves the supervisor–pup contract before adding complexity in later versions.

---

## 2. What Ships in V0.1

### Included

- `./vendor/bin/kanine serve` — boots the supervisor, binds an HTTP server, logs to screen and file via Monolog until Ctrl-C.
- GitHub issue fetching: reads open issues with label `kanine: ready` from configured repos.
- In-memory task queue: issues become tasks; each task is assigned to at most one pup.
- Pup protocol (minimal): `POST /pups/register` and `POST /pups/{id}/poll`.
- `bin/kanine --pup`: registers with supervisor, polls for tasks, runs `claude --headless` with the issue body as the prompt, in the pup's current working directory.
- Config: `kanine.yaml` (or defaults) drives repo list, label filter, supervisor host/port, and GitHub token.
- PHPUnit tests for all pure-logic components (config, task queue, pup registry).

### Explicitly Out of Scope

- TUI / terminal rendering (`php-tui` not used).
- Git worktrees (future V0.2+).
- Task status updates from pup to supervisor (`POST /tasks/{id}/status`).
- Question/answer flow (`POST /tasks/{id}/questions`).
- Task completion endpoint (`POST /tasks/{id}/complete`).
- GitHub label write-back.
- TLS / remote pups (localhost only in V0.1).
- Multi-task per pup (one task per pup at a time; blocked-and-double-task flow is future).

## 3. Domain Model

| Concept | V0.1 definition |
|---|---|
| **Supervisor** | The `kanine serve` process. Owns the task queue and pup registry. Embeds an HTTP server. |
| **Pup** | A long-running process that registers, polls, and runs `claude --headless` on assigned tasks. Operates in its own current directory. |
| **Task** | A GitHub Issue (from a configured repo, filtered by label) that the supervisor has queued for dispatch. |
| **Task queue** | In-memory list of tasks; FIFO; each task is either `queued` or `assigned`. |
| **Pup registry** | In-memory map of registered pups. Tracks `pup_id`, `hostname`, auth token, status, and assigned task. |

```php
enum TaskState: string
{
    case Queued   = 'queued';
    case Assigned = 'assigned';
}

enum PupStatus: string
{
    case Idle    = 'idle';
    case Working = 'working';
}
```

## 4. Functional Requirements

### 4.1 Supervisor — startup and config

- **FR-1** `./vendor/bin/kanine serve` starts the supervisor.
- **FR-2** Config is resolved in this order: `--config=<path>` → `./kanine.yaml` → `~/.config/kanine/kanine.yaml` → built-in defaults.
- **FR-3** Config must include at minimum: GitHub token (env var or config key), repo list, label filter, supervisor host/port.
- **FR-4** On startup, supervisor fetches open issues from all configured repos, filters to `kanine: ready` (or the configured label), and populates the in-memory task queue. Logs each queued issue via Monolog.

### 4.2 Supervisor — HTTP API

- **FR-5** Supervisor binds on `supervisor.host:supervisor.port` (default `127.0.0.1:3737`).
- **FR-6** `POST /pups/register` — accepts `{ pup_id, hostname }`, issues a bearer token, returns `{ token, poll_interval_ms }`. Logs registration via Monolog.
- **FR-7** `POST /pups/{pup_id}/poll` — requires `Authorization: Bearer <token>`. Accepts `{ status }`. If pup is idle and tasks are queued, assigns next task and returns `{ new_task }`. Otherwise returns `{ new_task: null }`. Logs assignment via Monolog.
- **FR-8** Unauthorized requests (missing/invalid token, unknown pup_id) return standard error JSON and appropriate HTTP status codes.
- **FR-9** All supervisor activity (startup, registration, task assignment) is logged to screen and rotating log file via Monolog.

### 4.3 Pup — lifecycle

- **FR-10** Pup is invoked with `KANINE_SUPERVISOR_URL` and `KANINE_PUP_ID` env vars set.
- **FR-11** On startup, pup POSTs to `/pups/register`, stores the returned token and poll interval.
- **FR-12** Pup polls `/pups/{id}/poll` every `poll_interval_ms`. When a task is assigned, pup logs the task details via Monolog, then runs `claude --headless` in its current working directory with the issue title + body as the prompt.
- **FR-13** While `claude --headless` is running, pup continues polling (with `status: working`). The poll response may return `new_task: null` since pup is occupied.
- **FR-14** After `claude` exits, pup resumes polling with `status: idle` and is eligible for the next task.
- **FR-15** Pup logs all activity (registration, poll responses, task receipt, claude start/exit) to screen and rotating log file via Monolog.

### 4.4 Config schema (V0.1 subset)

```yaml
github:
  repositories:
    - owner/repo
  token_env: GITHUB_TOKEN       # env var name; falls back to `gh auth token`
  ready_label: "kanine: ready"  # issues with this label are queued

supervisor:
  host: 127.0.0.1
  port: 3737
```

## 5. Non-Functional Requirements

- **NFR-1** PHP 8.2+. No extensions beyond `ext-json` and `ext-curl` (standard).
- **NFR-2** Supervisor HTTP server must not block the main process; pup polls must be handled concurrently with the tick loop. Use `react/http` or `symfony/process` as appropriate.
- **NFR-3** A pup calling `claude --headless` must not block the pup's poll loop. Run claude as a subprocess and poll concurrently.
- **NFR-4** Task queue and pup registry are in-memory; data is lost on supervisor restart. This is acceptable for V0.1.
- **NFR-5** Config loader, task queue, and pup registry must be unit-testable without network or process I/O.
- **NFR-6** All errors (GitHub API failure, malformed request, missing env var) produce a clear message to screen and log file and do not crash silently.

## 6. Technical Architecture

### 6.1 Components

```
kanine/
├── bin/
│   └── kanine          # `kanine serve` = supervisor; `kanine --pup` = pup
├── src/
│   ├── Console/
│   │   ├── Application.php
│   │   └── Command/
│   │       └── ServeCommand.php       # `kanine serve`
│   ├── Config/
│   │   ├── Configuration.php
│   │   └── ConfigLoader.php
│   ├── Supervisor/
│   │   ├── Supervisor.php             # top-level coordinator
│   │   ├── TaskQueue.php              # in-memory FIFO queue
│   │   ├── PupRegistry.php            # registered pups + tokens
│   │   └── HttpServer.php             # HTTP API handler
│   ├── Logger/
│   │   └── LoggerFactory.php          # Monolog: stderr stream + rotating file handler
│   ├── GitHub/
│   │   └── IssueLoader.php            # fetch + filter issues → Task[]
│   ├── Pup/
│   │   ├── PupClient.php              # HTTP client for supervisor API
│   │   └── ClaudeRunner.php           # wraps `claude --headless` subprocess
│   └── Domain/
│       ├── Task.php
│       ├── TaskState.php              # backed enum
│       ├── Pup.php
│       └── PupStatus.php             # backed enum
├── tests/
└── config/
    └── kanine.dist.yaml
```

### 6.2 Concurrency approach

PHP is single-threaded. Two loops must co-exist:

- **Supervisor:** Uses `react/http` (non-blocking) to handle pup HTTP requests while the main loop ticks periodically to log heartbeats and detect stale pups.
- **Pup:** Uses `symfony/process` to spawn `claude --headless` as a subprocess. The pup's poll loop uses `Process::isRunning()` to check claude's state each tick without blocking.

### 6.3 New Composer dependencies (beyond existing)

| Package | Purpose |
|---|---|
| `react/http` | Non-blocking HTTP server for supervisor |
| `knplabs/github-api` | Fetch GitHub issues |
| `symfony/process` | Spawn and monitor claude subprocess in pup |
| `guzzlehttp/guzzle` | HTTP client for pup → supervisor requests |
| `monolog/monolog` | Dual-channel logging (stderr stream + rotating file handler) |

## 7. Pup Protocol (V0.1 subset)

Full protocol is in `docs/architecture/pup-protocol.md`. V0.1 implements:

### Register

```
POST /pups/register
{ "pup_id": "uuid", "hostname": "string" }
→ 200 { "token": "t_...", "poll_interval_ms": 5000 }
```

### Poll

```
POST /pups/{pup_id}/poll
Authorization: Bearer <token>
{ "status": "idle" | "working" }
→ 200 { "new_task": Task | null }
```

`Task` shape:
```json
{
  "id": "uuid",
  "issue_number": 42,
  "repo": "owner/repo",
  "title": "string",
  "body": "string (markdown)"
}
```

All other endpoints from the protocol doc are **not implemented** in V0.1.

## 8. Phases

### Phase 1 — Supervisor skeleton

**Goal:** `./vendor/bin/kanine serve` starts, binds HTTP, and responds to requests. No GitHub yet.

Tasks:
- Add `react/http` to `composer.json`.
- Implement `ServeCommand` that boots `Supervisor` and starts the HTTP server.
- Implement `TaskQueue` (enqueue, dequeue, peek) with unit tests.
- Implement `PupRegistry` (register, lookup by id, token validation) with unit tests.
- Implement `HttpServer`: wire `POST /pups/register` and `POST /pups/{id}/poll` to `PupRegistry` and `TaskQueue`. Return hardcoded stub tasks for now.
- Add `ConfigLoader` support for `supervisor.host`, `supervisor.port`.
- Log all events to stdout with timestamp.

**Done when:** `./vendor/bin/kanine serve` starts, a curl to `/pups/register` returns a token, a subsequent poll returns `{ new_task: null }`.

---

### Phase 2 — GitHub issue loading

**Goal:** Supervisor populates task queue from real GitHub Issues on startup.

Tasks:
- Add `knplabs/github-api` to `composer.json`.
- Implement `IssueLoader`: fetches open issues from configured repos, filters by `ready_label`, returns `Task[]`.
- Wire `IssueLoader` into `Supervisor::boot()` — queue all loaded tasks before accepting connections.
- Add `ConfigLoader` support for `github.repositories`, `github.token_env`, `github.ready_label`.
- Unit test `IssueLoader` with a mock GitHub client.
- Log each queued issue (repo, number, title) to stdout on startup.

**Done when:** With a real `kanine.yaml` and `GITHUB_TOKEN` set, `./vendor/bin/kanine serve` logs the fetched issues and a poll returns one as `new_task`.

---

### Phase 3 — Pup client

**Goal:** A pup process can register and poll the supervisor over HTTP.

Tasks:
- Add `--pup` flag to `bin/kanine` entry point (reads `KANINE_SUPERVISOR_URL`, `KANINE_PUP_ID` env vars).
- Add `guzzlehttp/guzzle` to `composer.json`.
- Implement `PupClient`: wraps HTTP calls to `/pups/register` and `/pups/{id}/poll`.
- Implement pup main loop: register on startup, poll every `poll_interval_ms`, log poll responses.
- When `new_task` is received, log task details to stdout (no claude yet — Phase 4).
- Unit test `PupClient` with a mock HTTP client.

**Done when:** `KANINE_SUPERVISOR_URL=http://localhost:3737 KANINE_PUP_ID=$(uuidgen) ./vendor/bin/kanine --pup` registers, polls every 5s, and logs received tasks.

---

### Phase 4 — Claude headless integration

**Goal:** Pup runs `claude --headless` in its cwd when assigned a task.

Tasks:
- Add `symfony/process` to `composer.json`.
- Implement `ClaudeRunner`: spawns `claude --headless` as a subprocess with the task title + body formatted as the prompt.
- Integrate into pup loop: on task receipt, start `ClaudeRunner`; set status to `working`; continue polling with `status: working` until process exits.
- On claude exit: log exit code and resume polling with `status: idle`.
- Unit test `ClaudeRunner` with a stubbed process (verify command construction, status transitions).

**Done when:** Pup receives a task, logs "Starting claude for issue #N", runs claude, logs claude exit, then polls again with `status: idle`.

---

### Phase 5 — Integration test and polish

**Goal:** Full end-to-end flow works reliably. V0.1 is releasable.

Tasks:
- End-to-end smoke test: supervisor + one pup, real GitHub issue, real `claude --headless`. Verify issue is fetched, assigned, worked, and pup returns to idle.
- Error handling: supervisor unreachable (pup retries with backoff), invalid token (pup re-registers), GitHub API failure (supervisor logs error, starts with empty queue).
- Graceful shutdown: `Ctrl-C` on supervisor logs shutdown; `Ctrl-C` on pup terminates claude subprocess cleanly.
- Config validation: clear error messages for missing token, unknown repo, invalid port.
- Review and tighten all stdout log output for readability.
- Tag `v0.1.0` release.

**Done when:** All acceptance criteria below pass.

## 9. Acceptance Criteria

| AC | Criterion |
|---|---|
| **AC-1** | `./vendor/bin/kanine serve` starts without error; logs bound address to stdout. |
| **AC-2** | `POST /pups/register` with valid JSON returns a bearer token and `poll_interval_ms`. |
| **AC-3** | `POST /pups/{id}/poll` with a valid token and `status: idle` returns the next queued task (if any). |
| **AC-4** | Supervisor logs each GitHub issue fetched and queued on startup. |
| **AC-5** | Pup registers, polls every `poll_interval_ms`, and logs received tasks. |
| **AC-6** | Pup runs `claude --headless` on task receipt; logs start and exit. |
| **AC-7** | Pup resumes polling with `status: idle` after claude exits. |
| **AC-8** | A second pup can register and receive a different task from the queue concurrently. |
| **AC-9** | Missing/invalid auth token returns `401`; unknown pup_id returns `404`. |
| **AC-10** | `ConfigLoader`, `TaskQueue`, and `PupRegistry` have passing PHPUnit tests. |
| **AC-11** | Ctrl-C on supervisor shuts down cleanly; Ctrl-C on pup terminates the claude subprocess. |

## 10. Open Questions (pre-V0.2)

- **Worktrees:** V0.2 will isolate each pup in a dedicated git worktree. Decide clone strategy (clone on pup startup vs. supervisor pre-clones) before implementation.
- **Task persistence:** In-memory queue is lost on supervisor restart. V0.2 candidate: flat JSON or SQLite sidecar.
- **Completion signal:** V0.1 has no `POST /tasks/{id}/complete`. V0.2 should wire task completion → GitHub label write-back to move issues off `kanine: ready`.
- **Question flow:** Full question/answer protocol (per `pup-protocol.md`) is the V0.2+ target once the basic dispatch loop is stable.
- **Concurrent tasks per pup:** Protocol supports a pup working two tasks when blocked on a question. Defer until question flow is implemented.
